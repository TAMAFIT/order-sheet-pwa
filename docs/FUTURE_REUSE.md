# 将来の再利用案 — 確定申告・経費書類自動集計

このリポジトリの再利用候補として、手書き注文票ではなく、**印字された領収書・レシート・PDF・JPEG・スクリーンショット等を一括投入して構造化・集計するアプリ**を想定する。

## 想定入力

- Amazon領収書 PDF
- Amazon購入履歴・注文詳細のスクリーンショット
- ECサイトの領収書 / 請求書
- スキャンPDF
- JPEG / PNGの領収書
- 店舗レシート
- メール添付の請求書
- カード利用明細のスクリーンショット
- その他の綺麗に印字された文書

## なぜ今回の基盤を使えるか

手書き注文票で問題だったのは、崩した日本語と二次元的な人物・商品境界の認識だった。

確定申告向け文書では、一般に次の点で条件が良い。

- 印字フォント
- 明確な日付・金額
- 定型ラベル
- PDF内テキストを直接取得できる場合がある
- 店舗名や注文番号等の重複検出キーを持ちやすい
- 人物境界や手書き丸数字を読む必要がないケースが多い

そのため、同じ「AI → 構造化 → 例外確認 → 集計」でも、実用化可能性を別途評価できる。

## 推奨UX

目標は「全部確認」ではなく「問題だけ確認」。

```text
ファイルを複数投入
       ↓
文書ごとに自動解析
       ↓
共通スキーマへ正規化
       ↓
重複検出
       ↓
自動集計
       ↓
要確認だけ表示
       ↓
修正
       ↓
CSV / 会計ソフト用データ / 年間集計
```

例:

```text
52件読み込み
49件 自動処理完了
3件 要確認

- 日付候補が2つ
- 金額が不鮮明
- 既存領収書と重複の可能性
```

## 共通スキーマ案

最初から会計ソフト固有形式へせず、中間の共通形式を作る。

```json
{
  "document_id": "...",
  "source_file": "receipt.pdf",
  "document_type": "receipt",
  "date": "2026-08-15",
  "merchant": "Amazon.co.jp",
  "description": "USBケーブル",
  "amount_total": 1980,
  "tax_amount": 180,
  "currency": "JPY",
  "payment_method": "credit_card",
  "order_number": "...",
  "invoice_number": "...",
  "account_hint": "消耗品費",
  "confidence": 0.98,
  "needs_review": false,
  "review_reasons": []
}
```

必要に応じて明細行を別配列へ持つ。

## 要確認ルール候補

- 日付が取れない
- 金額が取れない
- 金額候補が複数
- merchantが不明
- 税区分が不明
- 同じ注文番号 / 金額 / 日付の重複候補
- confidenceが閾値以下
- 文書種別が不明
- 合計金額と明細合計が合わない
- ユーザーが会計科目の確認を必要とする

## 重複排除

確定申告用途ではVision精度と同じくらい重要。

重複キー候補:

- 注文番号
- 請求書番号
- merchant + date + amount
- ファイルhash
- 画像perceptual hash
- 同一PDFページhash

「Amazon領収書PDF」と「同じ注文のスクリーンショット」が両方投入されても二重計上しない設計が必要。

## AI処理方式の候補

将来はCustom GPT経由に固定しない。

候補:

1. Custom GPT + Action
2. OpenAI等のAPIをサーバー側で利用
3. PDFテキスト抽出 + AI補正
4. OCR + LLM構造化
5. provider-agnostic backend

大量ファイルを「適当にぶち込みまくる」用途では、最終的にはサーバー側APIの方がバッチ処理・進捗・再試行・コスト管理を行いやすい可能性が高い。

## 開発開始時の最初の実験

新アプリをいきなり作り込まず、最初に30〜100件程度の実文書で次を測定する。

- 日付正解率
- merchant正解率
- 合計金額正解率
- 税額正解率
- 重複検出率
- 要確認率
- 1件当たり処理コスト
- 1件当たり処理時間

このベンチマークで実用性を確認してからUIを拡張する。

## このプロジェクトから得た最重要原則
