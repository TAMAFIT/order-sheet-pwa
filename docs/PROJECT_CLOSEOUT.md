# Project Closeout — 手書き注文 集計アシスタント

- Closeout date: 2026-08-15
- Final experimental version: `v0.1.19`
- Frozen snapshot branch: `archive/final-v0.1.19-2026-08-15`
- Previous review-first snapshot: `backup/v0.1.18-review-first`
- Status: **FROZEN / experimental reference**

## 1. 目的

固定フォーマットの手書き注文票をスマートフォンで撮影し、AIで商品名・数量・注文者境界を解析して、最終的に商品別の買い付け数量へ自動集計することを目的に開発した。

最終的な目標は、人間が注文票を読み直して転記・集計する作業をできるだけ減らし、画像1回の投入から実用的な買い付けリストを得ることだった。

## 2. 到達した構成

最終版では次の流れまで実装した。

1. PWAで注文票を撮影または端末画像から選択
2. 画像にSCAN_IDを付与
3. 専用Custom GPTへ画像を渡す
4. Custom GPTが固定帳票ルールで解析
5. `submitScanResult` Actionを1回実行
6. Cloudflare Workerが結果を受信
7. KVへSCAN_ID単位で一時保存
8. ユーザーがPWAへ戻る
9. PWAが結果を取得
10. 商品別集計を即表示
11. 判読不明・低confidence・数量不確実等だけを「要確認」に分離
12. 必要な明細だけ編集・削除・追加・並べ替え
13. 修正後の集計へ即時反映
14. セッション履歴・復元・共有・印刷

## 3. 実装して有効だった要素

### SCAN_IDによる結果の非同期返却

ChatGPTとPWAが直接同一画面上で接続できなくても、SCAN_IDを共通キーにすることで、Custom GPTのAction結果を外部ストア経由で元アプリへ戻せた。

この方式は特定の手書き注文票に依存せず、別のAI書類処理にも再利用できる。

### Custom GPT Action → Worker → KV

Custom GPTから外部APIを呼び、結果を一時保存し、クライアントが後から取得する構成は成立した。Secretはクライアントへ持たせず、Action/Worker側で管理する設計とした。

### 「全部確認」から「例外だけ確認」への改善

初期は各認識行を人間が1件ずつ確定しないと集計できなかった。最終版では、解析後すぐ集計結果を作り、怪しい項目だけ要確認へ出す設計へ変更した。

このUXは今後の領収書・レシート・PDF処理に特に再利用価値が高い。

### 後編集と履歴

商品名、数量、取消、追加、削除、並べ替えを後から修正でき、結果は自動再集計される。セッション単位の復元とローカルDBのバックアップも実装した。

## 4. 実用化を見送った理由

最大のボトルネックはPWAやAction連携ではなく、**日本語の手書き文字と帳票レイアウトをVisionモデルが安定して認識する精度**だった。

実際の帳票では、次の誤りが実務上無視できなかった。

- 崩した日本語商品名の誤読
- 商品名中の規格数字と注文数量の混同
- 丸数字の読み落とし
- 注文者名と商品名の境界の誤認
- 下段の商品が上段の注文者へ所属するなどの人物取り違え
- 二次元配置を縦方向・横方向の異なる順で読む問題
- 同じ帳票でも撮影条件や筆跡で結果が変わる

固定帳票ガイド、詳細なInstructions、読み順の明示、色の扱い、商品DB照合、後確認UIなどを追加したが、入力認識の根本的な不安定さを十分には解消できなかった。

人間が全件確認する設計にすれば精度を補えるが、それでは「画像1枚から高速に集計する」という省力化の目的が弱くなる。

そのため、2026-08-15時点では手書き注文票用途として本番導入せず、実証プロトタイプとして凍結する。

## 5. 失敗ではなく、切り分けられた結論

今回の実証で分かったことは次の通り。

- PWAでの撮影・ファイル入力: 実現可能
- ChatGPT/Custom GPTへの引き渡し: 実現可能だがモバイルUI制約あり
- GPT Actionによる外部返却: 実現可能
- Worker/KVによる一時結果ストア: 実現可能
- PWA復帰後の自動取得: 実現可能
- 構造化結果の自動集計: 実現可能
- 例外だけを人間に確認させるUX: 実現可能
- 日本語手書き商品名を実務レベルで常時正確に読む: **今回の条件では不十分**

つまり、書類AI処理基盤の多くは再利用でき、手書きVision入力だけが今回の主な不採用要素である。

## 7. 将来の再利用候補

最も有力な次用途は、確定申告・経費整理向けの文書自動集計。

対象候補:

- Amazon領収書 PDF
- ECサイトの領収書・請求書
- JPEG/PNGの領収書
- 印字レシート
- スクリーンショット
- メール添付PDF
- その他の印字済み帳票

これらを一括投入し、文書種別・日付・店名・金額・税額・摘要・支払情報等へ構造化し、重複検出・要確認・集計・CSV等の出力へつなげる構成が考えられる。

詳細は `FUTURE_REUSE.md` を参照。

## 8. 再開判断

手書き注文票用途を再開する場合は、UI開発より先に実データによる認識ベンチマークを行うこと。

再開候補条件:

- 日本語手書きVision精度が大幅に改善
- 固定帳票向けOCR/VLMが低コストで利用可能
- 構造化画像解析の再現性が改善
- 帳票自体をQR/JAN/チェック式等へ変更可能
- 訂正コストより自動化メリットが大きくなる業務量になった
- VoiceDev OSの別機能として同じAction返却基盤が必要になった

## 9. 最終判断

このリポジトリは削除せず、**手書き注文票Vision実証 + AI→外部アプリ結果返却基盤の技術資料**として保存する。

次回は「手書きを読む」ことを前提にせず、入力品質が高い印字PDF・領収書・レシート・スクリーンショット等から再利用を検討する。
